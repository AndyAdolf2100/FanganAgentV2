# 普通网页 PPT 流程只读审计

日期：2026-09-30。范围：当前工作区代码、项目 skill 与非敏感配置；未修改运行代码、未重启任务、未调用生成模型。本文件的“已证实”指能从当前控制流直接确认；不代表已经用新样本复现了全部视觉后果。

## 结论

普通与企业模式目前只共享了一部分工具，尚未共享一套完整的质量闭环。普通模式主要是“模型规划简稿＋少量重点页定制＋规则/母版排版＋有限视觉修补”；企业模式是“模板约束合同＋逐组完整 HTML＋浏览器/视觉修复”。企业模式近期新增的换正文模板、即时反馈自修复、已有版本继续优化，没有完整下沉为普通模式也能用的能力。

因此，仅继续增加 skill 提示词或换更强视觉模型，不能保证最终变好。当前主要约束是动作权限、内容与分页冻结时机、完成状态定义和回路覆盖面。应保留现有可靠的来源与品牌校验，将两种模式放在同一执行内核上，以不同设计政策控制自由度。

## 实际流程与已具备能力

普通入口见 `marketing/marketing_agent/presentation.py:237`：

1. `read_manuscript`：Markdown 解析为稳定块 ID，初始分节分页。
2. `prepare_assets`：查文稿与风格关联缓存，必要时预留 cover/scene1/scene2。
3. `understand_reference`：视觉模型独立分析风格参考，生成文字形式的视觉要求。
4. `plan_outline`：GLM 输出页型、结论文案、来源 ID、视觉主题。
5. `edit_deck`：GLM 精简容量、安排图片与构图，随后锁定逐页文案。
6. `generate_or_reuse_images`：GLM 写图片任务单，项目工具调用 Seedream，后续产品场景可引用 cover。
7. `generate_pages`：少数重点页完整生成 HTML/CSS；其余可复用模块原型、适配母版、结构化版式。
8. 浏览器探针、必要的规则拆页、导出 HTML/PPTX 和截图。
9. 对全部成品逐页单图视觉审查，主 Agent 选修复页，再生成 HTML、探针、重渲染、单图复查。
10. 规则检查通过后任务标记 completed；视觉结果另存。

值得保留的现有能力：

- 模型设计与宿主验证分工清楚；`PresentationAgent.call` 留有实际工具轨迹，见 `presentation_agent.py:17`。
- 普通页通过 `text_catalog` 与 `data-ref` 绑定锁定文字，避免修 CSS 时悄悄改数字、丢文字，见 `presentation_pages.py:120`。
- 图表来源绑定到原稿表格单元格，宿主读取数值；普通与企业最终复用 `validate_chart`，见 `presentation_charts.py:25`、`enterprise/adaptive.py:217`。
- 每个实际成品视觉请求只有一张截图；参考模板在独立步骤分析；真实模型响应与工具调用留档，见 `presentation_vision.py:76`、`:96`。
- 图片与视觉有持久化预算、缓存与文件锁；页面写入有版本检查，见 `presentation_budget.py:17`、`presentation_pages.py:183`。
- 企业模式发布快照、人工品牌保护、正文重选模板和完整 HTML 自修复，是可以成为统一内核的已有基础。

本机配置快照（不含任何密钥）：重点页 6 页、页面模型调用 14 次；Seedream `doubao-seedream-5-0-flash-260915`、2048×1152、累计图片请求上限 100；视觉 `doubao-seed-2-1-pro-260915`、累计视觉请求上限 1000；图片类预算 20 元、图片与视觉共享预留上限 100 元。此处是本地预留策略，不是服务商实际扣费。

## 已证实的问题与最小改法

### G01 · completed 不表示达到可交付质量（P0）

**证据**：`presentation.py:296–310` 仅检查 `report['passed']`；视觉结果为 `needs_review`、`incomplete` 或未启用仍可 completed。企业同样在 `enterprise/model_html.py:574–584` 将视觉结果单独记录后 completed。`PresentationJobs.create` 的重试条件只含 image_notice 或 visual incomplete，未涵盖 needs_review，见 `presentation.py:170–172`；普通任务同参数再次生成可能直接返回旧成品。现有 `/optimize` 又限定企业任务，见 `presentation.py:193–201`。

**影响**：用户看到生成结束，却仍需 Codex 或人工发现显眼缺陷；普通任务也缺少同项目版本化再优化入口。

**最小改法**：独立 `execution_status`、`quality_status`、`release_status`。浏览器通过先进入可预览草稿；中高问题、缺图、缺少终审不得标为最终质量通过。两种模式共用优化入口，并保留旧版本。预算用完可停在 needs_review，不能冒充成功或无限重试。

**验收**：注入一次视觉 medium 和一次视觉服务失败，两种模式都能看到草稿和准确待办，但无“质量验收通过”；修复后新 artifact hash 与报告 hash 一致，才生成最终交付标记。

### G02 · 普通 Agent 可执行动作太窄，无法解决问题根因（P0）

**证据**：`presentation_agent.py:78–104` 唯一允许工具 `repair_page`，排除 chart，明确禁止新增图或付费重生成；`presentation_vision.py:163–200` 只允许 CSS/构图改变，文案不得增删。普通视觉阶段先冻结分页，且重渲染要求页数和文字目录不变，见 `presentation_vision.py:209–212`、`:245–249`。企业视觉修复也要求返回原生成组页数，见 `enterprise/model_html.py:438–439`。

**影响**：文案过量、需要拆页、需要换图、数据图标签过密、模板不适配，常被迫只改 CSS；更强模型也无法使用未开放的动作。

**最小改法**：将动作分为低风险布局修复、换素材、重选正文模板、重做图表规格、重分组/拆页、允许提炼模式下的文案再编辑。每个动作声明会使哪些检查失效；保留不可变来源，重新建立目录、页码及覆盖映射，而不是永久冻结页数。固定企业页只允许其对应的受限动作。

**验收**：相同拥挤正文分别在企业、普通模式中触发项目 Agent 自主拆页或换布局，事实/来源无丢失；图表问题可以修而不是只记日志；整个过程无 Codex 改 HTML。

### G03 · 普通 HTML 个性化覆盖率很低，母版优先于模型设计（P1）

**证据**：`presentation_pages.py:329–330` 默认 4 个重点页、最多 12 页，默认 8 次页面模型调用、最多 36 次；本机配置为 6/14。`select_custom_pages` 决定候选且截断，见 `:281–302`。`generate_page` 在模型之前尝试 `load_master`，只对 brand_launch 且有 layout_brief 的页例外，见 `:241–249`。`load_master` 又优先 `adaptive_master`，见 `:50–58`；该母版是固定几何的 bands/timeline/house/hero CSS，见 `presentation_masters.py:17–54`。

**影响**：结构稳定但变化和内容适配有限；“主 Agent 已写布局 brief”并不意味着该页实际由模型实现。很多页面仍然是换色、换文字的规则版式。这是实现事实，不能误称已实现全页模型自主设计。

**最小改法**：每页明确 `design_origin`（模型、已验收模板、旧缓存、降级）及选择理由。母版作为模型可选初稿，不能以浏览器无溢出直接当审美通过。无需机械要求每页从零写 HTML，但每页都进入相同质量闭环；不合适的母版能被拒绝和替换。

**验收**：24 页普通稿中所有页都有设计来源与质量状态；高密度页不因重点页名额用完被永久锁在差版式；新增行业样本不能只有配色变化。

### G04 · 修复覆盖与停止策略不适合长文稿（P0）

**证据**：普通模式 `presentation_vision.py:222–226` 固定 2 轮、每轮至多 3 页，每页 HTML 最多 2 次尝试（`:180`），最多只有 6 个动作名额，可能反复用于相同页。企业普通生成也是每轮 3 个动作；仅显式优化分支提高到 40，见 `enterprise/model_html.py:522–524`。企业还有即时浏览器/视觉候选反馈 3 次重试，而普通分支没有同等闭环，见 `enterprise/model_html.py:545–564`。

**影响**：若 30 页中 10 页存在真实问题，普通流程在数学上就不可能保证全部处理。用户增加视觉上限也不会突破动作上限。

**最小改法**：一个持久化问题队列驱动循环；每个问题绑定候选版本、尝试次数、修复动作与效果。单一方法连续失败后换动作或升级，直到全册满足质量门禁、没有可改进候选或达到明确资源上限。轮数可以有安全限制，但不应把“每轮 3 页”当长文稿质量策略。

**验收**：至少 12 个不同页问题的夹具全部进入处理队列；重复失败不饿死其他页；每个未解决问题都有停止原因与已用动作，不出现“达到轮数所以质量通过”。

### G05 · 普通视觉修复的候选提交语义与 skill 承诺不一致（P0）

**证据**：普通 `repair_page` 浏览器通过即写入 `plan`（`presentation_vision.py:195`）。全册 render 失败会回滚（`:250–255`），但修复后视觉 verdict 为 fix 时只更新视觉报告，不回滚此候选（`:257–265`）；视觉服务失败也保留已替换版再返回 incomplete（`:267–268`）。而 `agent-workflow.md:13` 写“失败恢复上一个可导出版本”。企业当前有浏览器＋视觉均通过才接受的候选循环，见 `enterprise/model_html.py:556–571`。

**影响**：普通流程可能接受视觉上更差但 DOM 合法的候选；“修了”不等于“改好了”，没有统一的 best-known 版本。

**最小改法**：通用候选事务：生成 candidate → 硬检查 → 单图视觉 → 与 incumbent 按同一 rubric 评价 → 接受/保留。未复查候选只能作为草稿，不覆盖已验收版本；无需要求每次必须审美分数上涨，但不可新增高危问题、破坏已通过项目。

**验收**：人为令候选浏览器通过但新增视觉 high，旧版保持已验收；候选、反馈仍能查看。普通与企业行为一致。

### G06 · 图片链只在普通生成的前半程执行，修复阶段不可补齐（P0）

**证据**：普通流程在 `presentation.py:256` 与 `:273` 接入图片工具；企业正式入口早在 `:243–246` 分流，`enterprise/model_html.py:411–456` 的计划/生成 payload 未接通 `prepare_assets`/`materialize_assets`。普通只有全部资产为空时才预留 3 个槽位（`presentation_images.py:53–59`），有任意匹配资产就不创建新需求。图片失败后删除引用并将 image 页改 statement（`:130–140`）；视觉修复发现无资产时只标 needs_assets（`presentation_vision.py:233–235`）。导演明确禁止生新图，见 `presentation_agent.py:81`。

**影响**：企业正文无法像普通稿一样按内容调用 Seedream；普通稿已有一张图也可能压掉新增必要场景的需求。首次生图失败、主体构图不合适时，后续优化没有补救动作。

**最小改法**：把 `asset_requirements → asset_registry → generate/edit/reuse → image_inspect → place` 做成共用工具链；由实际页需求创建不限于固定名称的素材任务，但每次受预算控制。企业品牌/模板图片不可替换；只在正文合同允许区域生图。资产失败由导演选择延期、重试、无图方案，且记录质量目标是否降级。

**验收**：企业正文有明确场景需求时能在项目工具日志看到 GLM 图片 brief、Seedream 调用、资产检查和 HTML 引用；固定品牌 checksum 不变；错误图片可通过同 Agent 自修复，不能仅靠 Codex 下载替换。

### G07 · 仍有行业案例特判和资产缓存语义不足（P1）

**证据**：`presentation_images.py:45–52` 只要文稿含“轻芽”就复制仓库 cover/office/outdoor，可能覆盖前面按文稿/风格取得的同名资产。`asset_cache_dir` 只以 source_sha256＋style_id 缓存（`:65–69`），未包含实际主题色、图片模型/图片提示词版本。`materialize_assets` 对资产成功只做解码、尺寸验证，没有独立的品牌主体/用途/构图质量检查；图片工具验证见 `:229–244`。

**影响**：某个示例看起来好，不能推导任意企业或新行业都好；同稿自定义色谱变化时可能继续用旧色彩图。资产可读取不等于可用。

**最小改法**：案例素材迁入显式用户资产或测试夹具；缓存使用资产任务内容 hash 与实际视觉主题/模型版本；补资产验收并保留复用 provenance。不要用正文关键词决定生产配图。

**验收**：同稿换色后仅在素材仍满足新主题时复用；不含旧行业信息的文稿不会收到旧包装；同产品多张图具有可核对的主体一致性。

### G08 · 普通“来源完整”与企业“正文完整”是不同政策，不能共用一个含糊通过位（P0）

**证据**：普通 `validate_design` 把未映射块补进末页 blocks/notes，见 `presentation_design.py:126–130`；`refine_design` 明确正文可提炼删重复，完整原文保留备注（`presentation_editorial.py:15–18`）。普通渲染 `verifyNotes` 只要求原稿块在某页备注存在，见 `design.mjs:22–26`；报告也明确 `source_coverage_mode=full_original_in_speaker_notes`，见 `render.mjs:262`。但 skill 要求预算、KPI、时间、受众、执行动作应可见，见 `marketing-deck/SKILL.md:46`，当前没有对应的逐项可见覆盖验收。企业生成则检查实际 HTML 的源块覆盖，见 `enterprise/model_html.py:452`。

**影响**：普通稿可合法通过来源检查，但关键执行要点只在备注。另一方向，把企业逐字保留政策直接套普通稿也会导致冗长拥挤。

**最小改法**：统一 `ContentContract`，明确 `verbatim` 与 `presentation_summary` 两种内容政策；保留不可变事实与必须可见的要点 ID、允许提炼项、备注专用项。企业与普通都报告可见覆盖、备注覆盖、数字/单位一致性，不能把备注完整当作叙事完整。

**验收**：刻意漏掉关键预算或行动要点但保留全部备注，必须被检查器发现；摘要模式允许压缩文字但不可丢条件；逐字模式自动拆页而不删原文。

### G09 · 图表数据校验可靠，但缺修复工具与表达容量（P1）

**证据**：普通允许 bar/column/line/donut，类别、序列受容量限制，见 `presentation_charts.py:5`、`:29–42`；chart 页被禁止 custom/composition/附加 items（`presentation_design.py:54–58`）；普通导演排除 chart，修复工具直接抛“本轮仅记录视觉建议”（`presentation_vision.py:165`）。渲染发现 chart 标签溢出直接抛错（`render.mjs:228`）。企业复用同一数值校验，但 `enterprise/adaptive.py:217–228` 目前只从一个列生成一个序列，且默认拿整张表的所有行。

**影响**：超过 6 类、长标签、多序列或“图＋解释”需求缺少自动解决路径；企业虽然能放图表容器，其数据规划能力比普通的 series 结构还窄。

**最小改法**：共用 `chart_spec`，支持明确的行子集、多序列、分组续图；模型可以改类型、图框、标签策略、分页，宿主继续固定取数和单位。生成离线 SVG，PPTX 使用相同规格导出原生图表；不允许用 AI 图片冒充数据图。

**验收**：8 类长标签、2 序列数据在两种模式都能自行拆成可读图；各图源单元格一致，合计/分类未丢；视觉错误能触发修复工具。

### G10 · 只看单页的视觉模型无法判断整册节奏；全册首轮后才纠错过晚（P1）

**证据**：普通完成所有页面后才运行 `review_and_repair`（`presentation.py:289–293`）；企业同样先生成与导出再全册审查（`enterprise/model_html.py:502–516`）。当前 `_review_page` 明确只有一个截图，禁止凭单页猜其他页（`presentation_vision.py:118`）；普通导演接收 findings、layout/layout_brief，未接收全册结构统计或实际审美对比摘要（`presentation_agent.py:84–85`）。已有一致性工具偏字号/字体，见 `render.mjs:249–251`。

**影响**：一种差布局可以传播多页后才发现；每页均 pass 不代表全套节奏、色彩、密度和重点表达优秀。

**最小改法**：保留用户要求的“一次一张截图”；先生成代表页并逐张验收，再生成后续 3–5 页小批次。每批聚合页型、留白、文字密度、图文面积、色彩、焦点位置、视觉 verdict，交导演做全册层面的决策；整册最后冻结，逐张终审并做结构统计审查。模板参考分析单独进行。

**验收**：前三页相同拥挤布局被发现后，后续页直接采纳新的模块约束；连续重复且无叙事原因的结构被整册审查识别；仍能证明每个实际视觉调用只有一个成品截图。

### G11 · skill、内联 policy、配置存在漂移（P1）

**证据**：`agent-workflow.md:11` 仍写“最多 5 张”，而 `screenshot-review.md:6` 与代码已严格单图；前者 `:13` 写 2 轮×3 页，企业优化代码却是 3 轮×40；普通 skills 描述 6/14 是当前机器配置，不是 `presentation_pages.py:329–330` 的默认 4/8。企业 `skill_text` 通过 Markdown 标题字符串截取普通页文件的一段原则，见 `enterprise/model_html.py:62–63`。大量关键 policy 在 `presentation_editorial.py:13`、`presentation_images.py:152`、`presentation_vision.py:22`、`presentation_agent.py:81` 内联。vendor 原件被作为调研来源，运行主流程读取的是项目适配后的 skill，不是任意 vendor skill 都参与调用。

**影响**：只把一个 SKILL.md 交给同事，不会得到现有工具链；文字描述与真实调用边界冲突，也可能误导导演选择无法执行的方案。

**最小改法**：一个版本化工具能力清单生成运行时可用工具描述、限制、错误码和预算；设计政策独立成资源，由两种模式显式组合，不依赖标题 split。交付包区分可执行代码、已接入 skill、目标 skill、调研 vendor 与真实验收证据。

**验收**：交接方只提供模型适配器、前端模板快照与存储即可运行；启动时能校验所有 skill 引用和工具版本；CI 检出“单图/多图”“允许动作/不可执行动作”不一致。

### G12 · 长任务恢复、缓存质量与成本账本尚未形成统一策略（P1）

**证据**：`PresentationJobs.recover` 将所有 running/queued 标记 failed，而非恢复阶段（`presentation.py:106–111`）；专用 resume 接口只对企业 refinement（`:223–229`）。普通页面模型结果在探针通过后即进入 page-cache（`presentation_pages.py:270–273`），以后缓存命中也仅探针再验（`:235–240`），虽后续仍会全册视觉审查，但缓存条目本身没有可信的质量标签。预算是 presentations 根下 image-cache/vision-cache 累计预留（`presentation_budget.py:10–14`、`:26–36`），不是按任务记录实际耗费；图片类另硬封顶 20 元（`presentation_images.py:186`）。

**影响**：恢复后会重复较多阶段；探针通过的差布局可能被持续复用。增加请求次数不等于能多优化；全局预留、项目预算、单任务预算、服务商实际费用容易被混为一谈。

**最小改法**：统一阶段 checkpoint 和 artifact/version hash、缓存标记 draft/hard_pass/visual_pass/final_pass；生产复用保留质量证据但必须检查输入、字体、模型策略版本变化。预算分账 account/project/job/tool，预留与确认消耗分离，缓存命中不重复算调用；失败不擅自清零历史。

**验收**：中断后从最后已验证组继续，已缓存成功图片不重生成；返回单任务与总额度的清晰停止原因；视觉未验收缓存不被当作高质量母版。

## 尚待验证的假设

以下不能仅由代码断言，应在后续独立实验验证：

- 更强 Pro 视觉模型能否稳定识别普通页的审美缺陷：需要同样本多次重复与人工标注；仅模型名变化不代表已达标。
- 普通页固定母版是否是用户认为“普通”的最大原因：需要对同内容做母版/模型设计盲评，不能只看一页。
- 企业正文约束导致的窄框问题是否仍在新模板重选后出现：需审当前版本真实截图和合同，不应仅根据旧样本归因。
- 模型是否在修复中不断变好：现在没有统一 best-candidate 评分与回归指标，需保存每轮相同页截图做对照。
- DOM 对比度基于最近不透明背景色，不能完全代表复杂图片/渐变下的实际对比度（`render.mjs:65–78`）；应以真实案例衡量漏检率，不直接宣称全部检查失效。
- HTML 合格不能证明 PPTX 应用渲染一致；报告明确 `pptx_application_render='pending'`（`render.mjs:263`）。用户主目标是网页 PPT，PPTX 导出应作为单独兼容门禁。

## 统一内核，保留两种政策

建议共享以下对象，而不是把普通模式直接改成企业模式：

| 共用对象/工具 | 统一责任 | 普通政策 | 企业政策 |
|---|---|---|---|
| SourceLedger / ContentContract | 原稿、事实、必须可见要点、备注映射 | 可选择演示摘要或全文 | 按业务选择全文/摘要；数字和事实相同保护 |
| DeckPlan / PageBrief | 叙事、页型、内容分组、素材与图表需求 | 风格 DNA 与模块约束 | 额外绑定企业模板版本、页用途与合同 |
| DesignContract | 可改与不可改区域、主题与字体 | 普通母版是可替换参考 | 人工品牌保护；固定页保构图、正文中央自由 |
| AssetRegistry / image tools | 复用、生图、参考编辑、质量验证 | 全页按内容需求选用 | 固定品牌保持；只在允许正文区域使用新资产 |
| ChartSpec / chart tools | 来源取数、绘制、测量、可编辑导出 | 可与解释内容组合 | 同工具但套企业主题与容器 |
| PageGenerator | 项目模型完整生成或依据已验收骨架生成 HTML | 接收普通合同 | 接收企业合同 |
| Probe / SinglePageReview | 浏览器事实与单张截图判断 | 共用错误协议 | 加品牌合同差异检查 |
| RepairDirector / CandidateStore | 选择动作、候选比较、回滚、局部重规划 | 可以改构图/素材/页数 | 动作受页用途及人工品牌保护约束 |
| FinalGate / ArtifactManifest | 冻结版本、完整性、逐页终审、质量结论 | 共用 | 共用，增加品牌一致性 |

建议先修 G01/G02/G04/G05/G06/G08，而不是先扩大提示词。其次统一单页生成接口与候选版本，再把图表、节奏和断点恢复整合。

### 兼容迁移：旧普通流程保持默认，新内核对照后迁移

用户明确要求过“原来直接生成网页 PPT 的模式的流程不变”。G03 是对现有设计来源和能力边界的审计，不是要求立即把普通页全部改成模型从零生成。现有重点页数量也不等于最终 `custom` 页面数量：后续页可复用原型与母版（`presentation_pages.py:347–359`），修复阶段还可以生成新 HTML。母版可复用、低延迟和模块一致性应保留；真正要纠正的是“无溢出就永久接受”和“失败后无其他可执行动作”，而非删除母版本身。

- **默认行为不变**：现有普通任务继续调用既有规划、摘要政策、素材、重点页选择、母版和导出路径；进行中的任务固定其原版本。企业新增能力不能仅因改动共享 `choose_repairs` 或视觉 policy，就自动改变普通任务的工具权限、页数、文案保留方式和费用。
- **新内核显式开关**：使用任务级 `workflow_version`／能力快照选择旧流程或新内核；创建时持久化，恢复时读取该快照。统一质量门禁、候选事务、错误分类与升级、增量渲染、共用资产各自声明版本与启用状态；仅新内核启用新的阻断式门禁或动作，旧任务可先追加观察报告，避免突然失去原来的可预览/下载结果。
- **隔离缓存与版本**：新旧任务、候选、检查报告、设计缓存必须包含执行器/政策/渲染器版本，不能因源文稿与 style_id 相同就复用另一流程的成品或覆盖旧质量报告。现有去重依赖 `pipeline_version`（`presentation.py:163–172`），新开关须纳入同一判定；版本切回也应保留新版本草稿供检查。
- **固定样本对照**：使用当前普通流程已有的优质样本，加长正文、表格/多序列图表、无配图、不同风格与版式样本。先离线对同一冻结输入比较事实/可见要点、主题和模块一致性、HTML/PPTX导出、审美盲评、耗时、调用量；不能用“HTML 全由模型输出”作为胜出指标。生图/视觉双跑会产生费用，只对明确批准的回归集执行，不默认让所有生产任务影子双跑。
- **先公共基础，再设计路径**：先把错误协议、候选保存、增量渲染等能力封装成可选工具，并验证旧适配器产物与既有版本一致；新普通生成与新企业生成都通过各自政策调用它们。母版选择、全页设计范围、图片策略变化留到新内核对照验收后再迁移，不在一次共享模块重构中顺便改变。
- **迁移与回退门槛**：旧流程默认保留至固定样本没有关键回归，且新流程自动修复、审美与可靠性有可复核提升；再经用户/产品方明确确认更改默认。单个新任务失败可保留旧版成品，状态注明失败/待审；不可静默退回旧引擎后声称新内核验收通过。

## 如何证明超过 118

“超过”应有可复核标准，不能以模型自评 pass 或 skill 数量为依据：

1. 建立相同文稿、相同企业模板、相同页面/内容要求、相近资源预算的测试集；覆盖企业/普通、图表/表格、密集长稿、缺素材、弱模板、短标题与多层章节。
2. 分开统计事实与内容完整、品牌保持、可读性、布局美观、图像语义、整册节奏、自动修复成功率、无需人工干预比例、耗时与费用。
3. 硬性项先门禁；审美用匿名成品的人工盲评，并保留单页及整册理由；自动视觉用于运行期评审，不能同时充当唯一的“胜出证明”。
4. 118 对话中的方案属于对方陈述；要区分对方展示/实测能力、对方建议、我们的推断。不能用“对方说有某 skill”替代真正的效果比较。
5. 对交接同事交付可运行工具协议、已接入 skill、验收脚本、固定样本、最终 artifact manifest 与失败案例；不要只交一个描述目标的 skill 文件。

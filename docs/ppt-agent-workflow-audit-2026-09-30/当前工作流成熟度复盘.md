## 4. 仍阻碍稳定交付的问题

### P0：来源规划会制造重复目录

第 2 页已有正式目录，第 3 页又出现“提案总览（完整目录）”。根因在 model_html.py 的来源页型限制：非标题原稿块只能进入正文/序言，且明确要求原稿目录列表进正文；正式目录则另用 agenda_ids 生成。

### P0：历史视觉问题的关闭必须有证据，补强代码尚未进入当前 worker

目录同一 HTML/截图曾在 v3 被报告短尾换行，v4 的新 initial 检查给出 pass，却没有逐条 recheck。新的通过不能自动代表旧问题已经修好，也可能是审查判断变了。

### P0：还缺一次真实完整成品验收

56 页的整册独立视觉终审、历史问题闭环、素材落位及当前导出版本检查尚未全部完成。当前局部通过不足以宣布“完善”或“超过 118”。保持 needs_review 是正确行为；必须以同一冻结版本完成验收。

### P1：修复稳定性不足，增加次数不能替代修复策略

来源组 g23（原第 25 页）蓝色箭头内“调性 × 视觉 × 文案”裁字被 Seed 确认。GLM 三次修复分别出现漏原文“留”、多出“好”、标题宽度 1098.33 与批准值 1068.33 不一致。校验正确拦截了新错误，但原问题稿仍待审。

建议按错误类型约束修复范围：协议/JSON 错误只修响应结构，文字覆盖错误精确保留原文，局部裁切只调整相应正文组件；只有版式确实容纳不了时才重选模板或重新分页。仍由 GLM 输出完整 HTML，但降低无关文字与固定区域变化。记录每类错误的修复成功率，而非只统计调用次数。

### P1：模板导入与字体保真有上游缺口

parser.ts 当前跳过 SVG/EMF/WMF 图片，以及部分图表、表格和嵌入对象；复杂背景/形状也可能近似还原。后续与导入后的 HTML 比较，无法证明它等于原 PPTX。

服务端缺字体目前会告警，但不阻止发布。应提供逐页、逐对象的损失记录，保存实际渲染字体及已接受的替代方案，再确认模板发布。前端拆分和打标的职责保持不变。

“可以生成数据图表”与“能从任意 PPTX 导入原有可编辑图表并保真”不是同一个能力。后者尚不具备。

### P1：模板选择和美观规划应前置

首次选模板主要拿到名称、截短样例和标签数量；更丰富的视觉限制在选完后才分析。修复时虽可切换正文模板，仍偏向失败后的补救。短文本试填也不能揭示长标题、长列表、表格或复杂图形的真实容量。

建议在发布时形成每套模板的布局资料：可用正文区、标题容量、图文占比、色彩/字体、适合内容类型、图表样式及形状内安全区域。规划时先匹配内容密度和表达方式，再生成页面。保留来源覆盖，同时避免额外摘要与完整段落重复展示。

应使用多套真实模板和不同长度文稿建立验收样本：既测内容完整与不溢出，也检查阅读顺序、留白、重复版式节奏和主题一致性。检查次数更多并不直接代表更美观。

### P1：普通模式尚未得到同等交付保证

按用户此前要求，普通网页 PPT 入口和主体流程保持。它现在会逐页初审，最多两轮修复、每轮最多三页，只复查已改页面；没有企业 v5 的独立全册终审、候选版本验收和稳定问题关闭机制。图表页目前还被排除在普通自动修复之外。

普通任务可能在浏览器检查通过、视觉仍待审时被标为 completed。后续宜共享质量状态、问题记录和终审工具，同时保留普通模式的设计自由与入口。此次没有改动普通流程，也没有新的普通稿真实验收。

## 6. 建议推进顺序与“完善”的判定

1. 完成当前轮并保留未通过问题；受控加载历史问题补强，复核旧问题，不能用旧 pass 跳过。
2. 修正规划中的目录重复，给新规划单独版本及回归，不直接删成品页或覆盖旧任务。
3. 用真实失败页验证错误分类修复是否收敛，再完成当前整册独立终审和 Codex 抽查/复核；不通过则继续保留草稿。
4. 补上导入损失、字体确认、模板容量与布局资料，验证多套真实模板，而不只优化当前茶饮稿。
5. 在不改变普通模式设计入口的条件下统一质量状态和终审能力，分别验收企业/普通场景。
6. 最后同步源代码、skills、工具协议、部署要求、样例、测试和真实验收证据，重建 manifest/ZIP，再做从干净环境运行的交接验证。

可以宣布达到交付要求的最低证据是：没有遗漏或重复消费来源；固定企业元素保持；所有最终页经过视觉审查；未解决问题为零或具有明确且可审计的接受理由；审查与实际交付文件为同一版本；多套模板回归通过；交接包能独立复现。视觉模型通过后仍需独立审美复核，不把模型自评当作美观保证。

## 7. 优先采用的快速收敛方案

用户追问是否有更快的解决办法。建议先减少无效返工，再考虑增加并行度；不需要先更换 GLM/Seedream/Seed，也不以降低视觉验收标准换速度。以下是建议，尚未因此修改在途任务或部署代码。

### 先按错误类型分配修复任务

| 错误 | 建议处理 | 避免的浪费 |
| --- | --- | --- |
| JSON/协议不合法 | 在当前步骤纠正响应结构；浏览器和 Seed 不接收无效候选 | 没有可渲染页面时重复截图、调用视觉 |
| 来源漏字、多字、固定品牌被改 | 明确给出差异及原始不可变内容，让模型恢复该部分；记录与视觉问题为不同原因 | 让 Seed 反复发现本可由代码判定的问题 |
| 局部裁切、换行、间距或对比度 | 提供目标元素、实测尺寸、邻接关系和允许修改范围，要求局部改变样式/结构 | 为一个标签重排其他页面区域并引入新问题 |
| 版式根本容纳不了内容 | 在三轮修复预算内尽早更换同套合适正文模板、重排自由区或分页 | 对狭窄箭头反复缩小字体、硬塞内容 |
| 重复目录 | 在来源规划时合并目录承接关系并证明覆盖 | 生成完成后让视觉模型猜测哪页该删除 |

模型仍完整输出页面 HTML。新增的是对允许改动区域的明确限制和提交差异校验，不由 Codex手改成品、不用固定坐标规则替代模型布局。完整来源不能丢，修复失败时也不能用静默替换文字来掩盖。

### 三轮修复有不同职责

首轮优先解决明确的局部问题；若浏览器/Seed 证据说明模板容量或结构不适合，第二轮就重排正文或换正文模板；第三轮只收尾并验证。是否升级应由失败原因决定，例如单纯 JSON 错误不能自动触发换模板。总次数仍受现有三轮自我修复限制，不增加隐含的无限循环。

封面、目录、章节、尾页及固定品牌元素继续受原约束。正文可以换布局，但页眉、页脚、标题区域、主题和来源完整性必须通过检查。失败则保留草稿及原因，不能标成通过。

### 把重复成本移出每页循环

模板分析、字体确认和容量资料按模板版本缓存；素材按用途及内容指纹缓存；候选阶段优先复验发生变化的页面。缓存键必须包含模板版本、HTML/截图哈希、审查规则版本与待关闭问题，不能凭旧 pass 跳过新问题。

最终仍对冻结后的全册做独立逐页视觉验收。候选阶段的通过不能替代终审。

生成侧可评估只读来源文本引用协议：GLM 决定完整 HTML 结构与排版，文字通过明确来源片段绑定、由工具校验展开，从根源减少逐字重写导致的漏字多字。这属于输出协议改造，须验证分段、富文本、图表标签和来源覆盖兼容后再采用，不能直接套到正在运行的旧版本。

### 并行是后续提速项

稳定后可让两个独立来源组同时处理，同一组的生成、检查、修复保持顺序；用单一提交点维护页序、版本、预算和最终冻结。当前逐组实现需要改造后才能安全并行，不能直接多开同一个任务。此举主要缩短等待，不会自动改善页面审美，也未实测加速倍数。

优先验证指标：同一错误重复率、每组 GLM 修复次数、首次候选通过率、模板重选后的通过率、最终未关闭问题数，以及每份稿的实际请求用量。先用 g23 裁字、长目录、长标题和密集 SVG 四类失败样本做回归，再扩展到多套模板。
